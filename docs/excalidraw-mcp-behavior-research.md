## Components and exposed tools

The server exposes five tools in this revision. The widget is a shared HTML resource (`ui://excalidraw/mcp-app.html`), rendered by a compatible host in an iframe. The server returns checkpoint data, not a screenshot: the React widget converts input elements to SVG inline and mounts the Excalidraw editor in fullscreen. Bifrost proxies the server-facing calls/resources; the host owns the view lifecycle and forwards input/results to the widget. [Server registrations](https://github.com/excalidraw/excalidraw-mcp/blob/157aa23ceb1976008aadc89eb05e3444060f09d6/src/server.ts#L405-L690) · [widget](https://github.com/excalidraw/excalidraw-mcp/blob/157aa23ceb1976008aadc89eb05e3444060f09d6/src/mcp-app.tsx)

| Tool | Audience | Function |
| --- | --- | --- |
| `read_me` | Model | Element-format instructions |
| `create_view` | Model/App, default visibility | Submit scene instructions; create a new checkpoint and return its ID |
| `read_checkpoint` | App only | Load a stored scene |
| `save_checkpoint` | App only | Replace stored data under the supplied checkpoint ID |
| `export_to_excalidraw` | App only | Compress/encrypt and upload a snapshot to the Excalidraw backend; return a share URL |

Export is separate from checkpoint saving or a live collaboration session. Its handler uploads encrypted data to `json.excalidraw.com/api/v2/post/` and returns an `excalidraw.com/#json=...` link. Export was not invoked in this study. [Export handler](https://github.com/excalidraw/excalidraw-mcp/blob/157aa23ceb1976008aadc89eb05e3444060f09d6/src/server.ts#L515-L602)

## `create_view` and checkpoint semantics

In the pinned server implementation, every successful `create_view` resolves the submitted elements, creates a **new** random checkpoint ID, saves the resolved scene under that ID, and returns the ID in `structuredContent`. When the input begins with `restoreCheckpoint`, the server loads the referenced checkpoint's `.elements`, filters IDs named by `delete` pseudo-elements, appends the new elements, then saves that merged scene under the new checkpoint ID. This is state continuation, not in-place update of the old checkpoint or a pane selector. [Pinned `server.ts`](https://github.com/excalidraw/excalidraw-mcp/blob/157aa23ceb1976008aadc89eb05e3444060f09d6/src/server.ts#L453-L507)

The app widget does receive complete/partial tool input and the tool result. Its `ontoolresult` handler records the returned checkpoint ID and uses it as the localStorage key. On later events with a checkpoint ID, it loads saved local edits for that key. This supports recovery for the same checkpoint; it does not match a new model invocation's newly returned checkpoint ID back to a particular old pane. [Pinned `mcp-app.tsx`](https://github.com/excalidraw/excalidraw-mcp/blob/157aa23ceb1976008aadc89eb05e3444060f09d6/src/mcp-app.tsx#L770-L829)

## Fullscreen edits and persistence

The widget requests fullscreen via `requestDisplayMode`, synchronizes the latest in-memory edited elements when returning inline, and also listens for host display-mode changes. The implementation's release history says fullscreen no longer unmounts/remounts when new calls arrive while fullscreen. This is evidence for retained editor behavior in that app, but it does not guarantee host pane reuse for each later model tool result. [Pinned `mcp-app.tsx`](https://github.com/excalidraw/excalidraw-mcp/blob/157aa23ceb1976008aadc89eb05e3444060f09d6/src/mcp-app.tsx#L670-L690) · [host-context and tool handlers](https://github.com/excalidraw/excalidraw-mcp/blob/157aa23ceb1976008aadc89eb05e3444060f09d6/src/mcp-app.tsx#L785-L829) · [v0.3.0 release notes](https://github.com/excalidraw/excalidraw-mcp/releases/tag/v0.3.0)

Excalidraw editor changes are debounced for 2 seconds. The widget writes live elements to browser `localStorage` under `excalidraw:<checkpointId>`, calls the app-only `save_checkpoint` tool with `{elements: live}`, and sends a compact description of changes through `updateModelContext`. `save_checkpoint` persists to the store; `read_checkpoint` is called by the widget when it resolves `restoreCheckpoint`. [Pinned `edit-context.ts`](https://github.com/excalidraw/excalidraw-mcp/blob/157aa23ceb1976008aadc89eb05e3444060f09d6/src/edit-context.ts#L8-L120) · [pinned server app-only tools](https://github.com/excalidraw/excalidraw-mcp/blob/157aa23ceb1976008aadc89eb05e3444060f09d6/src/server.ts#L604-L649)

Checkpoint store choices in the source are materially different: local `FileCheckpointStore` uses the OS temp directory and keeps at most 100 files; `MemoryCheckpointStore` is process-local and evicts oldest above 100; Vercel's `createVercelStore()` selects Redis when its URL is configured, otherwise memory. Redis sets a 30-day TTL. The remote deployment configuration is unknown, so no particular persistence or retention guarantee can be attributed to `mcp.excalidraw.com`. [Pinned `checkpoint-store.ts`](https://github.com/excalidraw/excalidraw-mcp/blob/157aa23ceb1976008aadc89eb05e3444060f09d6/src/checkpoint-store.ts#L5-L140) · [pinned Vercel entry](https://github.com/excalidraw/excalidraw-mcp/blob/157aa23ceb1976008aadc89eb05e3444060f09d6/api/mcp.ts)

## MCP Apps host contract and same-view question

The MCP Apps lifecycle has the host render a UI resource for a tool call and deliver tool input and its result to the view. Apps may call tools or update model context. The contract reviewed does not define a standard model-tool argument that targets a previously rendered view instance; placement/reuse of a new tool result is host behavior. [MCP Apps overview](https://apps.extensions.modelcontextprotocol.io/api/documents/overview.html) · [MCP Apps specification](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/draft/apps.mdx)

Partial input is explicitly preview-only: the host may send “healed” JSON that is still truncated/incomplete. The app receives complete input later, then the result. `requestDisplayMode` only requests fullscreen among modes advertised by the host; `updateModelContext` informs the model about current edits but does not persist them by itself or direct a later result into this view. [App API](https://apps.extensions.modelcontextprotocol.io/api/classes/app.App.html) · [MCP Apps patterns](https://apps.extensions.modelcontextprotocol.io/api/documents/patterns.html)

Therefore, the reported second `create_view(restoreCheckpoint, delete sun, add sun)` producing a new pane is consistent with the code: the scene is restored and extended, but the call creates a new checkpoint and returns a new tool result. A universal impossibility claim would be too strong: the upstream widget has retained-fullscreen behavior across incoming calls. The reviewed interfaces do not establish a stable API that makes a subsequent model call mutate **exactly** the already-open pane. It may reuse a retained view when a host delivers the new call to it; otherwise the host may render another tool-result pane.

## App-registered tools: a relevant extension path, not current Excalidraw behavior

The MCP Apps **draft** in the inspected SDK revision explicitly describes host-to-App `tools/list` / `tools/call`, `tools` capabilities, and `app.registerTool()` / `oncalltool` handlers. These tools execute in the existing App lifecycle and could provide a way to change the scene held by that App, if implemented and supported by the host. This is different from adding a pane selector to `create_view`. It would be incorrect to conclude that the MCP Apps architecture universally forbids in-place model-driven editing. [Pinned draft, host-to-App calls](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/specification/draft/apps.mdx#L1239-L1286) · [registration example](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/specification/draft/apps.mdx#L1760-L1845)

Excalidraw's examined widget initializes `useApp` with `capabilities: {}` and registers neither `oncalltool` nor App tools. Its package requests ext-apps `^0.4.0`; the separate reference host used ext-apps 2.0.3. Support for App-registered tools in the user's Codex host has not been established, and no upgrade or implementation is proposed as already validated. [Widget initialization](https://github.com/excalidraw/excalidraw-mcp/blob/157aa23ceb1976008aadc89eb05e3444060f09d6/src/mcp-app.tsx#L1000-L1011) · [dependencies](https://github.com/excalidraw/excalidraw-mcp/blob/157aa23ceb1976008aadc89eb05e3444060f09d6/package.json)

## Progressive rendering

The host delivers model argument fragments through `ontoolinputpartial`; the widget parses the available elements, drops the last potentially incomplete item, and redraws when the completed element count changes. Final `ontoolinput` takes a different branch that renders the complete scene. Camera transitions and SVG drawing effects do not by themselves establish live partial input. HTTP/SSE transport and sticky MCP connections do not create host-to-widget partial argument events. The actual Codex behavior therefore still needs a timed observation/event trace. [Input rendering paths](https://github.com/excalidraw/excalidraw-mcp/blob/157aa23ceb1976008aadc89eb05e3444060f09d6/src/mcp-app.tsx#L426-L539) · [event handlers](https://github.com/excalidraw/excalidraw-mcp/blob/157aa23ceb1976008aadc89eb05e3444060f09d6/src/mcp-app.tsx#L804-L829) · [existing local research](mcp-apps-realtime-research.md)

## Qualification of local test evidence

The smoke assertions that call `save_checkpoint` with a raw JSON array and then read back the same value prove only that the save/read round trip returns that payload. `restoreCheckpoint` expects the stored object shape `{elements: [...]}` and reads `base.elements`; those assertions do not exercise restoration after editing, the widget's debounced save path, host view identity, or hosted checkpoint lifetime. No live diagram mutation or production call was made for this research note; the synthetic check below was local.

A separate synthetic check imported the pinned `edit-context.ts` and used mocked `localStorage` and app methods. After the 2-second debounce, a changed element position/version caused a localStorage write, `save_checkpoint` with `{elements:[...]}`, and an `updateModelContext` diff. When the mock save result carried `isError: true`, the widget code still published the context diff because it only catches rejected promises and does not inspect an MCP error result. Changing only text while preserving geometry caused localStorage/save calls but no context diff: `computeDiff` currently compares additions, removals, and position/size, not text/color changes. This is synthetic source-level evidence, not a live host or remote deployment test. [Pinned `edit-context.ts`](https://github.com/excalidraw/excalidraw-mcp/blob/157aa23ceb1976008aadc89eb05e3444060f09d6/src/edit-context.ts#L30-L120)

The pinned source's tool list contains no `read_widget_context` handler, subscription, polling, or server push mechanism; that name appears only in `create_view` instructional text. It should not be represented as a callable upstream tool based on this snapshot. [Pinned `server.ts`](https://github.com/excalidraw/excalidraw-mcp/blob/157aa23ceb1976008aadc89eb05e3444060f09d6/src/server.ts#L490-L507)

## Bifrost logs as a complementary debugging source

Existing isolated-candidate logs were inspected on 2026-09-27 without changing log level or restarting the gateway. `normal.log` records both first-boot VK/Virtual MCP association failures (`FOREIGN KEY constraint failed`) at 14:31:56 +02:00. `normal-restart.log` contains HTTP access records for all three routes, with timestamp, HTTP status, duration and request ID. It has no `[mcp-apps]` / `[mcp-server]` debug events at the current logging level. A status 200 alone does not distinguish a successful tool result from a JSON-RPC or `isError` failure.

The candidate already implements targeted debug events: App admission (`app_safe`, tool count), ambiguous callback rejection, UI resource read success/denial/failure, tool handler start (name and argument count), and native tool completion (`result_present`, `is_error`). These are emitted by `logger.Debug` in [the local MCP handler](../transports/bifrost-http/handlers/mcpserver.go). They can distinguish an absent callback from a rejected/failed callback in a fresh controlled reproduction when the candidate is started at debug level. They do not record browser drawing, DOM updates, or host-to-iframe partial input. No production logs were accessed and no runtime logging configuration was modified in this study.

A useful reproduction correlates: the exact user action and chat/tool call; a narrow timestamp window in Bifrost logs; the specific tool/resource result; then the visible existing App. Check `save_checkpoint` after a manual edit settles, validate its stored `{elements: [...]}` payload via readback, and separately exercise restoration. Do not infer same-view success from a `create_view` success log. Preserve view/checkpoint identity and distinguish host-only events such as `updateModelContext` from calls crossing the gateway.

## Limits

Source behavior is verified against the pinned commit only. The version currently deployed at `mcp.excalidraw.com`, its store configuration, retention in practice, and pane-reuse behavior in the user's host remain unverified. The current findings do not imply the hosted server matches this commit.
