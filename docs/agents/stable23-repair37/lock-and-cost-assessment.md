# Refresh mutex scope and lock ordering

Inspected all current SyncMCPServer callers: handler constructor; transport Add/Reconnect/Update/Credentials/Remove/Disable/Enable client operations; SetClientTools; asynchronous SyncMCPServersAfterToolsChange; synchronous final boot sync. Each operation returns from the config/client mutation before calling sync. The tools-change callback is fired outside MCPManager.mu and dispatches persistence/sync in separate goroutines; SetClientTools also releases mu before invoking its callback.

Lock order: handler.syncMu -> GetAvailableMCPTools -> core GetAvailableToolsForMCP/getAvailableTools -> manager GetToolPerClient/GetClientByName read locks (released on return). Server adapter only creates BifrostContext. CodeMode GetTools reads definitions. No dial, plugin execution, DB write or reverse call into SyncMCPServer occurs in this capture path. buildServer constructs a fresh MCP server, metadata/resources/handlers and callback aliases; registration does not execute handlers and cannot reenter sync. Its internal locks belong to an unpublished new server. Debug logging follows publication under the deferred unlock. No existing lock inversion or reentrant repository caller found.

Request paths still atomic.Load one immutable server/alias snapshot and do not acquire syncMu. Existing request admission and live visibility filtering remain unchanged. Registration still removes tools and aliases absent in the captured latest catalog; the mutex does not union/retain obsolete entries.

Cost: one constant-size sync.Mutex per long-lived handler (8 bytes on current linux/amd64), freed with the handler, no per-key/per-request retained state. Complete refresh capture/build/publication now queues under contention by design. No claim of zero refresh cost; serial/parallel refresh and unchanged ordinary HTTP request benchmarks are measured before/after using identical test functions, toolchain, local sources and 3 samples. Timing is observational on shared Cloud hardware, not a performance gate or speedup claim.

Harness coverage: the fork-only frozen D already has strict modern, first/second, direct/Virtual/aggregate catalog and denied-grant wire controls. Product C does not carry the fixture/orchestration collection. The new defect is a scheduler interleaving of internal refresh captures; no external HTTP request can deterministically hold that capture without adding a test-only public hook. The approved regression therefore uses the existing injected MCPToolManager seam and observes actual public HTTP tools/list and callback behavior. No new wire shape, collection/driver mutation or redundant passing case is introduced. The frozen wire controls remain required at the future full qualification; they are not executed or relabeled as passing here. This is a recorded concurrency-test boundary decision, not a claim that catalog regressions are invisible over HTTP.
