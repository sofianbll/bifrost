## Necessary delta by area

### Product behavior

- **Code Mode error semantics (#28):** In `core/mcp/codemode/starlark/executecode.go`, classify nested results only by MCP `CallToolResult.IsError`; do not infer failure from text beginning `Error: `. Keep the nested protocol error as a Starlark value. Actual JSON-RPC/transport, interpreter/sandbox, and post-hook guardrail failures remain outer failures. The test changes in `core/mcp/codemode/starlark/toolerrormarker_test.go` cover unmarked prefix text, marked and unmarked responses, and actual RPC failure; `core/internal/mcptests/codemode_security_test.go` retains output redaction/blocking controls. `examples/mcps/error-test-server/main.go` adds a deterministic `prefix` response.
- **MCP error marker (#28, needed for the Code Mode contract):** In the public `tools/call` handler, copy `ChatToolMessage.IsError` onto the MCP `CallToolResult` while retaining returned text. The end-to-end handler test checks that a real Code Mode outer failure survives the JSON-RPC boundary.
- **First-boot file config ordering (#29):** Keep client config loading/reconciliation in `loadMCPConfig`, but move `reconcileVirtualMCPsConfig` and source-of-truth pruning to a helper called after `loadGovernanceConfig` in `LoadConfig`. This ensures virtual-key rows exist before grants attach while preserving client-name resolution and existing pruning semantics. It is startup-only. The focused config-store lifecycle test must cover first boot and same-config restart, one attached key, and real governance admission; use the existing Python fixture config for the e2e control.
- **App discovery and in-memory representation (#30):** Preserve upstream tool definition, modern and legacy `_meta.ui.resourceUri`, visibility, and supported output schema as an internal bounded sidecar on a tool. Prefer modern URI if both are supplied. Keep metadata out of model/provider JSON. Mark source client after list-tools hooks. Include sidecar metadata in the tools hash so metadata-only updates persist; enforce the existing patch's 256 KiB bounds and fail-closed oversized visibility behavior.
- **Cache lifecycle (#30):** Add additive per-tool sidecar encoding/decoding at every MCP discovered-tools persistence boundary: RDB update and row save/load. Preserve the flat tool-map shape for older readers and support flat legacy cache reads. Tests must cover old-shape compatibility, metadata refresh, metadata-only hash changes, manager reload, and a refresh while upstream is available followed by cache use after upstream loss. Docs should state that an old writer can drop the sidecar and rediscovery restores it; this is not rollback support.
- **Catalog separation (#30):** Keep App-only tools out of model-facing catalogs unless explicitly also model-visible. Provide a native MCP catalog that includes app-only callbacks, including linked tools from Code Mode clients, while ordinary Code Mode tools remain excluded. Carry effective post-hook behavior: native `CallToolResult` fields (content, `structuredContent`, `_meta`, `isError`) survive for Apps, but stale native output must be discarded if hooks changed the compatibility result. Ordinary MCP tools keep their existing compatibility-message result path.
- **Negotiation and gateway relay (#30):** Advertise `io.modelcontextprotocol/ui` and its HTML MIME only when requested in initialize. Retain/emit the upstream App definition and supported output schema. Namespace resource URIs by source client and upstream URI; list only resources linked to currently admitted tools; resolve reads through the matching source client and MCP hooks, then rewrite returned content URIs to the gateway URI. Same upstream URIs from distinct clients must remain distinct. Preserve the established admission, visibility, per-request include-list, and hook permission controls. App-only bare callback aliases resolve only for one admitted source; ambiguity is generic and sources stay out of the response.

## Material decision and boundaries

1. **Stable config ordering:** The stable source currently reconciles Virtual MCPs inside `loadMCPConfig`, which runs before `loadGovernanceConfig`. Preserve file-authority/pruning semantics while moving reconciliation after governance. Do not alter auth, source-of-truth policy, migrations, or permission boundaries.
2. **Qualification harness separation:** Product and stable regression/fixture files above belong in the candidate diff. The Actions workflow, source-pinning comparator/driver, report packaging, and Cloud bootstrap/orchestration are fork-only qualification material per #35 and must be tracked separately from the product diff. Reuse immutable driver `968d934...` unless a proven stable-only orchestration adaptation is required. No later-dev implementation or workflow history belongs in the stable candidate.
3. **No behavioral evidence yet:** This was a source audit only. It does not establish stable baseline red/green cases, a clean patch application, a build, race behavior, local module provenance, a candidate SHA, or actual reference-host rendering. Those are the next authorized Cloud tasks and must be characterized against exact unchanged stable before patching.
