## Findings

- **Code Mode error fix A (#28) remains distinct from upstream #8604.** Upstream #8604 merged as `f3e8c0caa7ff3214b503b4b1b31eaaf2e64c0fc3`. It changes Code Mode result decoding: JSON text blocks, `structuredContent`, and one layer of JSON-string-wrapped objects/arrays. A changes whether a remote protocol-marked error remains a script value and whether the outer HTTP MCP response retains `isError` after execution/hooks. These share the Code Mode result path but are not the same behavior or regression. Do not mark A absorbed; rebase and qualify its distinct assertions against current dev if that contribution is later chosen. [A #28](https://github.com/sofianbll/bifrost/pull/28) · [upstream #8604](https://github.com/maximhq/bifrost/pull/8604) · [merged source](https://github.com/maximhq/bifrost/tree/f3e8c0caa7ff3214b503b4b1b31eaaf2e64c0fc3/core/mcp/codemode/starlark)

- **First-boot grant fix B (#29) is absent from current official dev and v2.3.0 source.** At both official snapshots, startup calls `loadMCPConfig` before `loadGovernanceConfig` ([dev LoadConfig](https://github.com/maximhq/bifrost/blob/c7e789560616338dc9672a72bfff75aa0562d562/transports/bifrost-http/lib/config.go#L1202-L1213); [v2.3.0 LoadConfig](https://github.com/maximhq/bifrost/blob/9237ec06672406e437b3cb33fc793ffd0403b3ae/transports/bifrost-http/lib/config.go#L1202-L1213)). `loadMCPConfig` still reconciles `mcp.virtual_mcps` before returning ([dev reconciliation](https://github.com/maximhq/bifrost/blob/c7e789560616338dc9672a72bfff75aa0562d562/transports/bifrost-http/lib/config.go#L2335-L2349); [v2.3.0 reconciliation](https://github.com/maximhq/bifrost/blob/9237ec06672406e437b3cb33fc793ffd0403b3ae/transports/bifrost-http/lib/config.go#L2335-L2349)). B moves that reconciliation to after governance loading. Its fork PR reports a stock failure at base `83258b776c68e1e3d2c1ca0d08a31c2e5811344f`, and passing two-boot persistence, governance-admission, and route checks on candidate `1194291f60bf0894d8b0998e2725b583bfdf1b5c`. The change is present in fork integrated dev `850f64563ad1bf2b0db988334d12d34403c3848e`; standalone [#29](https://github.com/sofianbll/bifrost/pull/29) is closed unmerged. **Limit:** no current official-dev or v2.3.0 runtime reproduction was run here. The unchanged ordering plus historical test is source-level evidence that the risk remains, not a fresh runtime proof. This is a general config-startup defect, not inherently an MCP Apps feature; keep it a separate candidate bugfix unless maintainers identify it as a prerequisite of the agreed Apps setup. [fork integration #27](https://github.com/sofianbll/bifrost/pull/27)

- **Apps relay C (#30) overlaps only the generic `tools/call` result relay.** Upstream [#7689](https://github.com/maximhq/bifrost/pull/7689) is still open on `dev`; it proposes carrying the native MCP `CallToolResult` through the core and HTTP gateway, retaining content blocks, embedded resources/resource links, `structuredContent`, `_meta`, and `isError`. C adds Apps-specific negotiation, admitted App metadata/visibility and source identity, scoped `resources/read`, callback alias rules, cache sidecars, and host/route qualification. Treat #7689 as a possible generic result carrier to reconcile with if accepted; it does not implement the Apps resource lifecycle. [issue #7666](https://github.com/maximhq/bifrost/issues/7666) · [C #30](https://github.com/sofianbll/bifrost/pull/30)
