# Stable 2.3 MCP Apps qualification contract

**Decision:** Treat stable 2.3 compatibility as an independent qualification lane. The existing campaign is dev evidence only. A compatibility claim needs an immutable candidate derived from the exact transports/v2.3.0 commit and compared with that same stock commit. It does not establish that any implementation or backport exists today.

## Evidence boundary

The accepted destination is both an upstream-facing native MCP Apps contribution and a separate stable 2.3 compatibility claim ([map #31](https://github.com/sofianbll/bifrost/issues/31)). The detailed spec records 9237ec06672406e437b3cb33fc793ffd0403b3ae as the dereferenced stable tag and says the former integration qualified only against its dev base ([spec #21](https://github.com/sofianbll/bifrost/issues/21)). GitHub's compare API reports stock 83258b776c68e1e3d2c1ca0d08a31c2e5811344f is 110 commits ahead of that tag; the final integration 968d934ed4489f3fa0bb86fdae9197406c05b5fb is a later dev-based head. The historical [Actions run 38898815061](https://github.com/sofianbll/bifrost/actions/runs/38898815061) and its final report describe stock 83258…, candidate/harness 968d934…, and 39 Apps requests / 148 assertions. The report explicitly says stable 2.3 was not built. These results must not be relabelled as stable evidence ([final #26 report](https://github.com/sofianbll/bifrost/issues/26#issuecomment-6215707521)).

The pinned workflow checks out stock 83258…, candidate and driver separately, verifies each exact SHA and clean tracked state, records the stable SHA, then builds and tests only stock and candidate. The stable SHA is metadata, not a checkout/build target ([workflow at 968d934](https://github.com/sofianbll/bifrost/blob/968d934ed4489f3fa0bb86fdae9197406c05b5fb/.github/workflows/upstream-stack-qualification.yml)). Thus the current 39/148 comparison is useful harness evidence, not a v2.3 result.

## Smallest reproducible contract

1. **Freeze three source identities:** stock 9237ec06672406e437b3cb33fc793ffd0403b3ae; a candidate commit whose parent/history is demonstrably based on that tag; and the harness/driver commit. Verify exact HEAD and clean tracked trees for all three. Record the tag and candidate separately from the dev lane. Keep the current dev candidate 968d934… under its existing 83258… comparison.
2. **Run the same deterministic fixture contract against both stable sources** on disposable CI infrastructure. Keep named behavior sentinels and green controls, and report every request/assertion/skip. Require candidate green and the expected stable-stock red for each claimed fix; retain stock-compatible behaviors green. Re-derive expected red cases from the stable source instead of inheriting dev's historical count or forcing old failures to remain red.
3. **Prove the tested binary contains the checked-out candidate modules.** Reuse the workflow's local Go workspace, focused MCP/handler/store checks and race checks; inspect go version -m for the built gateway and assert local (devel) transports/v2, core, framework and governance modules. A successful fixture against published module versions is not candidate proof.
4. **Include the lifecycle gate for stable support:** fresh-store first boot must attach the file-declared Virtual MCP key exactly once, then restart the same candidate/container and same disposable store and prove the grant still works. Preserve authority, reset, auth-load and existing flat-cache read controls from the accepted spec.
5. **Require actual host rendering on the stable candidate.** Reuse the pinned ext-apps v2.0.3 host at 82221c0c8ce7661efa6771c9d461511b1650495f, record its source, and require successful SDK handshake, negotiated text/html;profile=mcp-app, rendered fixture view, native result/payload and save/read/change/restore callbacks with zero page errors. Preserve deliberate bad-state and notification-order controls. The host bootstrap adds only a local synthetic-auth seam and explicitly opts into the official UI capability ([bootstrap source](https://github.com/sofianbll/bifrost/blob/968d934ed4489f3fa0bb86fdae9197406c05b5fb/tests/mcpapps/bootstrap-reference-host.mjs)). Controlled partial-input replay is a protocol control, not native Codex or live-model streaming proof.

Publish sanitized source identities, toolchain, build/module manifest, candidate/stock reports, restart and host reports as one immutable run artifact. No provider, public App, production store, secret or deployment is needed. Keep fixture counts as observed output, not a brittle acceptance target.

## Candidate shape and unresolved points

For stable compatibility, **a tag-based candidate identity is required**; comparing the dev candidate directly to stable stock would confound 110 commits of unrelated drift. The smallest candidate should contain only the accepted product changes required by the stable contract and the tests/docs needed to prove them. The candidate can be adapter-free if those changes apply and work on the tag. Whether code adaptation is necessary is unknown until a later authorized implementation/build resolves API and behavior differences; this research does not establish that it cherry-picks cleanly.

Spec #21 currently says no parallel release-based implementation branch is required and treats stable as a comparison reference. That language is insufficient for the now-confirmed stable-compatibility destination. Revise the spec/tickets to add this separate candidate-and-evidence lane before implementation planning. This qualification contract sets gates only; it does not promise parity, backport feasibility, release readiness, upstream acceptance or deployment.
